# A20｜云函数间调用关系图谱——6 个云函数调用链、依赖关系、数据流向、故障传播路径

> 项目：harmony-app（铃语，鸿蒙适老化股票异动播报）。本篇是六云函数的全景图谱，自包含成文；每条边、每个数据资产都给文件路径与行号证据，全部来自本仓库源码通读（2026-09-23），未做云端实测。

| generate-tts | cloudfunctions/functions/generate-tts/index.js（403 行） | 白话播报音频合成 | 被 fetch-tushare-data callFunction（fetch-tushare-data/index.js:613）或 HTTP 按需调用 | 60s | 百炼 CosyVoice WebSocket（:189）、CloudBase 存储 |

## 二、调用链详解（七条边，逐条给证据）

### 链1：定时器 → fetch-tushare-data → generate-tts（唯一的函数间调用）

fetch-tushare-data 在信号卡合成阶段通过 `app.callFunction({name:'generate-tts', data:{alertId, text}})` 批量调用（index.js:611-626），仅对 `kind==='signal'` 的前 10 条（:595），且用 Promise.allSettled 保证单条失败不拖垮批次；返回体经 `result.value?.result?.success` 判定（:652）——callFunction 的返回包了一层 result，这个解包路径是联调时最容易错的点，图谱必须标注。同时并行跑 DKnowC 合规检查（:601-604），合规结果只加 complianceStatus 元数据不阻断（:629-646）。**全仓库云函数间 callFunction 仅此一处**（grep 验证）。

### 链2：fetch-tushare-data → alerts.json → get-alerts → 端侧卡片流（主干数据链）

生产：fetch-tushare-data 把异动合并进 `alerts/alerts.json`（saveAlertsToDB，index.js:497-558；下载旧文件 :505-512、serverTs 并发写保护 :518-524、按 alertId 去重合并 :527-535、保留 500 条 :537-540、上传 :549-552）。消费：get-alerts 下载同一文件（get-alerts/index.js:32-34，fileID 硬编码 :21），排序截断返回 `{items, serverTs}`（:64-68）。端侧：AlertPoller.ets:41 拼参请求，:79 返回 items，Index 卡片流渲染。注意 get-alerts 的 serverTs 用的是 `Date.now()`（:67）而非文件水位——与写入方的 serverTs（fetch-tushare-data:544）语义不同，这是 A17 篇 P0 修复项的图谱级佐证。

### 链3：alerts.json → broadcast-a2a → Supabase / 华为 Push Kit → 端侧通知（主动推送链）

broadcast-a2a 读同一 alerts.json（:32，与 get-alerts 逐行雷同的 getLatestAlerts :27-48），对每条 `kind==='signal' || direction!=='flat'` 的条目发推送（handleBroadcast :225-230）。推送前从 push_tokens 集合拉活跃 token（:119-123，失败回退环境变量单 token :124-129），先向华为 OAuth 端点换 access_token（:138-146），再 POST `messages:send`（:161-193），payload.data 内联 alertId/symbol/kind/audioUrl（:177-182）——这个 data 就是端侧 EntryAbility.ets:85-95 receiveMessage 解析的对象，构成推送→拉起→定位卡片的闭环。Supabase 广播独立并行（:53-89），未配置时跳过（:54-57）。已知问题注明：此 Push 需换华为 Push Kit REST（本代码已按 REST 实现），AGC 三环境变量未配置时整段跳过（:111-114）。

### 链4：端侧 → push-token-register → push_tokens（注册回填链）

端侧 PushService.ets:80-86 上报 → 云函数查重更新或插入（index.js:29-51）→ broadcast-a2a 的链3读走这份名单。这条链是链3的**前置供给**：没有链4的注册，链3的推送无人可发（只剩 env 兜底单 token）。

### 链5：generate-tts → 百炼 WebSocket / tts 目录 / alerts.json 回写（音频支线）

generate-tts 经 WebSocket 合成（:189 起，协议时序已按阿里云官方文档核实无误，见 A16 篇三），上传 `tts/{cacheKey}.mp3`（:310-334），写缓存 `tts-cache/{cacheKey}.json`（:96-116），并把 audioUrl 回写进 alerts.json 对应 alertId（updateAlertAudioUrl :122-164）。**回写这条边是图谱中最危险的一笔**：它下载-修改-整文件覆盖（:127-158），没有链2生产者那套 serverTs 保护——与链2形成对同一文件的读写竞态（见 5.4）。

### 链6：端侧 → get-alerts/generate-tts 的"按需补音频"（规划态）

已知问题载明"alerts.json 的 audioUrl undefined 端侧按需调 generate-tts"。现状核实：端侧**尚未**实装该调用——Index.ets:208-209 在无 audioUrl 时记日志静默跳过，:226 与 :390 都以 audioUrl 存在为前提。即链6是规划中的边，图谱如实标注"未实装"，避免后人误以为音频兜底已闭环。

### 链7：init-db → 数据库（运维支线）

init-db 建四个集合（init-db/index.js:15），但交叉核实（A18 篇 3.1）真正被链3/链4使用的 push_tokens 不在清单内，清单内四集合无一被运行时使用——图谱上这条边"画错了线"，本身就是一个待修缺陷。

## 五、故障传播路径（八条，逐条推演）

1. **Tushare 40101 → 东财降级**（已发生的已知问题）：callTushare 抛错（fetch-tushare-data/index.js:106-111，token 脱敏 :108）→ daily 失败被 catch 返 null（:353-356）→ movers 为空 → 返回 success:true items:[]（:579-586）。注意传播终点是**静默成功**：主流程靠名称映射的东财多级降级（:123-272：内存缓存→存储缓存→东财刷新→过期缓存→hardcoded-names.js→空 Map）兜住，但"当日异动其实没抓到"这一事实不会以失败形态上报，只能靠日志发现。
2. **generate-tts 失败 → audioUrl undefined → 端侧无播报**：百炼 task-failed/超时（generate-tts/index.js:272-277、197-201）→ callFunction 返回 success:false → 上游只记日志（fetch-tushare-data:656-662）→ alerts.json 无 audioUrl → 端侧静默跳过（Index.ets:208-209）。传播**有界且无害**：卡片照常显示，首屏永不空白约束不被击穿；但用户侧表现为"信号卡没声音"且无任何提示。
3. **tempFileURL 过期 → 播放失败**：audioUrl 是临时链接（generate-tts:320-326）→ 写入 alerts.json 与缓存被长期持有 → 端侧 AVPlayer 报 error（AudioPlayer.ets:34-37）→ onError 回调。传播终点是"点播报钮没声音"，与 2 同形但更晚发生，用户无从归因。
4. **generate-tts 回写覆盖 → 主数据丢失**：时序为 fetch-tushare-data 写入新一批 → generate-tts 持旧快照回写 → 新异动被旧文件覆盖（无 serverTs 检查，generate-tts:127-158）→ get-alerts/broadcast-a2a 读到旧数据 → 端侧丢卡、推送漏发。这是图谱上唯一一条**反向破坏主数据**的传播路径，P0 级。
5. **alerts.json 损坏/缺失 → 全读方空转**：get-alerts 与 broadcast-a2a 的 catch 都吞成空数组（get-alerts:47-50、broadcast-a2a:44-47）→ 轮询返回空 items、广播"success 但 items:[]"（broadcast-a2a:213-219）→ 端侧演示卡兜底（约束内）。故障被伪装成"无异动"，告警缺失（A17 篇五）。
6. **Push 未配置 → 推送链断 → 轮询兜底**：AGC 三变量空（broadcast-a2a:111-114）→ sendPushNotification 跳过 → pushCount=0。端侧 AlertPoller 5 秒轮询是架构级兜底（AlertPoller.ets:20-26 注释自证），传播**按设计终止**。
7. **push_tokens 缺失/污染 → 推送失效**：集合未建（init-db 清单缺陷）→ broadcast-a2a:119-124 读库抛错 → 回退 env 单 token（:124-129）→ 只有一台设备收到推送。或被垃圾注册污染 → 向伪造 token 推送 → 华为侧报错烧配额。
8. **QUOTA 内存态失真 → 生成静默放弃**：额度计数冷启动归零（generate-tts:28-51）→ shouldStop 永远偏低 → 超限时百炼侧失败 → 走路径 2。它是路径 2 的上游诱因之一。

## 六、重复逻辑与治理建议

图谱核对出三处复制粘贴：getLatestAlerts 在 get-alerts:26-51 与 broadcast-a2a:27-48 几乎逐行相同；ALERTS_FILE_ID 三处硬编码（get-alerts:21、broadcast-a2a:22、generate-tts:25）；CloudBase init 纪律不一（fetch-tushare-data:28-37 单例，generate-tts:63-66、get-alerts:28-29、broadcast-a2a:29-30 每调新 init）。云函数间无法共享模块，治理路径：短期统一各文件内常量与单例写法；中期按 A17 方案C 把 alerts.json 集合化，让 get-alerts/broadcast-a2a/generate-tts 回写全部改走数据库（读写语义由数据库保证，重复读文件逻辑自然消亡）；`serverTs` 语义统一为"文件/集合数据水位"（A17 篇 P0）。演进优先级：④回写加保护（止血）→ ①②集合化（治本）→ ③链6按需音频实装（体验闭环）。
