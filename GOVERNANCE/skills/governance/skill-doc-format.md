# 技能：技能文档编写规范

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.0 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语）

## 一、目的与适用范围

本规范约束 `GOVERNANCE/skills/` 目录下所有技能文档的编写与修订，包括 governance 子目录现有五个技能（24h-autonomy、changelog-format、skill-doc-format、learning-loop、handover-protocol）本身。技能文档的唯一定位：让一个没有本项目对话记忆的席位（新会话代理或人类接手者），凭文档本身就能正确、安全地完成一类任务。达不到这个定位的文字，不是技能，是笔记。

## 二、FORMAT_SPEC：结构骨架

技能文档八个必备段，顺序固定：

1. 标题与元信息：技能名、所属目录、版本号、日期、适用项目；
2. 定位与适用场景：解决什么问题、何时用，并明确何时不适用；
3. 前置条件：执行前必须存在的文件、状态、权限，含不可逾越约束的核对——适老化 28-34fp 大字白话卡片流、禁 K 线图等复杂图表、三条内容红线（承诺收益/保本、催促性指令、对外公开/收费）、Stage 模型 compatibleSdkVersion 20 / targetSdk 26 纯 ArkTS 零三方依赖、不推翻架构基调；
4. 方法主体：按步骤或维度分节展开，配表格、清单或代码示例；
5. 与工程的对接：引用真实文件路径说明方法如何落到本项目（如 EntryAbility.ets 的 Push 初始化与 onNewWant 带 alertId 拉起定位、Index.ets 的 List 卡片流与 5 秒前台轮询 AlertPoller 兜底、AudioPlayer 的 AVPlayer 播云端 TTS 音频流、PushService.ets 占位封装降级轮询、AlertFeed 数据契约）；
6. 边界与红线：本技能不能做什么、出现什么情形必须停手；
7. 操作清单：可打勾的速查步骤；
8. 自我评估：正确性/完整性/可复用性三维 1-5 分，各附一句话简述，再写字数与使用模型声明。

版本规则：实质内容修订递增小版本（v1.1、v1.2）；结论推翻或结构重排递增大版本（v2.0）；每次版本变化必须追加一条 CHANGELOG 条目。

## 三、质量门槛（五条硬门槛）

### 3.1 自包含

不出现"如前所述""如上次所说""群里那个问题"等依赖对话记忆的指代。一切背景要么写进文档，要么以文件路径引用；被引用文件必须真实存在，尚未建立的标注"规划中"。

### 3.2 正确

与工程现状一致。现状快照（截至 2026-09-23）：数据源 Tushare token 失效（40101）已降级东财 API；百炼 TTS 仅支持 WebSocket；broadcast-a2a 的推送需换华为 Push Kit REST；PushService.ets 保持占位封装，AGC 未配置前降级轮询；alerts.json 的 audioUrl 可能为 undefined，端侧按需调 generate-tts；FEED_URL 待 X 服务器落地，契约即 AlertFeed。技能内容与事实冲突时，以事实为准并立即修订文档、递增版本号。

### 3.3 可执行

步骤具体到"打开哪个文件、跑哪条命令、看哪个字段、按什么格式落账"。拒绝"酌情处理""视情况而定"这类把决策推回读者的写法；确需判断的地方，必须给出判断标准（如 24h-autonomy.md 的安全阀清单就是一组可对照执行的停手标准）。

### 3.4 合规

不泄露任何 Token/密钥，示例一律用 `<TOKEN>` 占位；不推翻架构基调；不把三条内容红线的违规表述当作"示例文案"写进文档；涉及合规判断的场景必须写明停手条件。

### 3.5 可持久化

Markdown 落盘于指定路径，文件名与主题一致、短横线命名，一个主题一个文件；正文汉字数不低于设定目标的 85%（本库技能文档常规目标 3000 字，即正文 ≥2550 汉字）；文末自评三维齐全且各附简述。

## 四、可复用性验证：冷启动测试

定稿前必须通过一次冷启动测试：

1. 开一个无本项目上下文的新会话，只给它技能文档路径与工程仓库路径；
2. 要求按文档完成该任务的最小闭环；
3. 观察三点：卡在哪里（文档缺信息）、错在哪里（文档误导）、多做了什么（文档冗余）；
4. 卡点与错点回灌修订文档；连续两次冷启动无卡点即可定稿。

无法执行冷启动时的替代验证：作者逐段自问"这一段的每个名词，读者能否仅凭本文档或被引用文件知道含义？"答不出的名词要么就地解释，要么给出可读的文件路径。自评"可复用性"打 5 分的前提是完成上述验证之一。

## 五、编写流程（六步）

1. 素材采集：从 CHANGELOG、incident 记录、learning-loop.md 第三步产出的"模式"中取材；
2. 沉淀价值判断：同类事件 ≥2 次，或单次影响足够大（触红线、阻断交付）才写技能；一次性小问题进 KNOWN-ISSUES.md 即可，防止技能库信噪比被稀释；
3. 按第二章骨架起草；
4. 过第三章五门槛 + 第七章自查清单；
5. 冷启动测试或替代验证；
6. 定稿落盘 + 追加 CHANGELOG 条目 + 登记进技能索引 `GOVERNANCE/skills/README.md`。

## 七、自查清单（12 项）

1. 新会话只读本文档能否完全理解，无需任何聊天记录？
2. 每个引用路径是否真实存在，或明确标注"规划中"？
3. 步骤是否可打勾执行、判断点是否给了标准？
4. 是否与 3.2 节现状快照冲突？
5. 是否有表格、清单或代码示例？示例能否在本项目语境下直接对读？
6. 是否泄露任何凭据？
7. 是否出现三条红线的违规示例文案？
8. 边界段是否写明"何时必须停"？
9. 自评三维是否各附简述并指向文中具体事实？
10. 正文汉字数是否 ≥2550（按 3000 字目标）？
11. 是否已追加 CHANGELOG 条目？
12. 是否已登记进 `GOVERNANCE/skills/README.md`？

## 八、自评示例对照

坏：`正确性：5分`——裸分数，无简述，无法审计。

好：`正确性：4分 第 5 节引用的 PushService.ets 占位降级逻辑与现状一致；但未覆盖 onNewWant 带 alertId 拉起定位的极端场景，已列为遗留。`——分数与文中事实挂钩，扣分点明确，读者可复核。

自评注水（三维全 5 分却给不出指向文档内容的简述）视为未完成自评，须重写。

## 九、反模式

1. 百科式写作：大段搬运领域通识，工程对接只字不提；
2. 邮票式文档：全文两三百字步骤列表，无前置条件、无边界、无自评；
3. 路径悬空：引用不存在的文件且未标注"规划中"；
4. 红线复述癖：把通用合规红线抄一遍充当边界段，不写本技能特有的停手条件；
5. 单点成文：一次偶发事件立刻写成技能，稀释信噪比（应先进 KNOWN-ISSUES）；
6. 僵尸文档：写完从不修订，工程演化后与现状脱节仍被引用。

- 完整性：4分 覆盖规范、门槛、验证、流程、模板、清单、反模式九大部分；未含文档自动度量工具（字数与链接检查脚本）的设计。
