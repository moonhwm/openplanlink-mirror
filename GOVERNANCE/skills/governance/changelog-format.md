# 技能：CHANGELOG 条目规范

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.0 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语）

## 一、目的与适用范围

CHANGELOG 是 harmony-app 治理体系的"时间线主账本"：任何席位（Moon 或各工程角色）、任何变更（代码、文档、配置、实验、事故处置、交接）都必须追加条目。本规范定义条目的五要素结构、标准模板、分类标签与质量门槛，适用于项目全生命周期的所有记录场景。

设计目标只有一个：让三个月后没有任何对话记忆的读者，凭单条条目就能还原"当时谁在什么阶段、动了哪个文件、出于什么依据、留下了什么坑"。

## 二、存放位置与追加规则

1. 单一账本：全项目仅 `GOVERNANCE/CHANGELOG.md` 一个账本，不按模块拆分，保证时间线全局可排序；
2. 倒序追加：新条目置于条目区顶部第一条；
3. 只追加不改写：已写入条目不得修改或删除；发现写错，另追加更正条目并引用原条目时间戳；
4. 时间戳格式 `YYYY-MM-DD HH:mm (+08:00)`；同批次多条目时间允许相同，用序号区分；
5. 无事之日不强制写"无异常"，但实验日、交接日、事故日、红线处置日必须有条目。

## 三、五要素详解

### 3.1 谁（WHO）

写席位与角色，不猜自然人身份。合法取值示例：`Moon`、`工程-端侧`、`工程-云函数`、`工程-数据源`、`治理-审计`。禁止"我""某人"这类指代；交接期写明来龙去脉，如 `工程-端侧(交接自Moon)`。

### 3.2 何时（WHEN）

时间戳 + 阶段标签。阶段取值固定：`常驻`、`实验24h窗口A/B/C/D`（与 24h-autonomy.md 的窗口命名一致）、`交接期`、`事故处置`、`复盘`。阶段标签让倒序阅读时能快速过滤出关键时期。

### 3.3 改了什么（WHAT）

必须给出可定位对象：文件路径（如 `entry/src/main/ets/pages/Index.ets`）、函数或组件名、云函数名、或文档路径。变更动词用白名单：新增/修改/删除/回滚/降级。一个条目只写一件事；一次提交包含多件事就拆成多条。

### 3.4 为什么（WHY）

写动机与依据。依据可以是：外部事件（如 Tushare 返回 40101）、合规红线要求、实验报告结论、已知问题编号、架构基调约束。禁止"优化""完善""调整细节"这类零信息量表述。

### 3.5 遗留什么（LEFT）

未完成事项、风险、接手提示，三选其多必须写；确无遗留也要显式写"无遗留"，不允许留空。这是五要素中最常被漏掉、却对接手者最有价值的一项。

## 四、标准模板

```markdown
- **[YYYY-MM-DD HH:mm (+08:00)] [WHO] [阶段标签]**
  - 改了什么：[变更动词] `文件路径` 的 [对象]，一句话说明。
  - 为什么：[动机]；依据：[外部事件/红线/报告/已知问题#编号]。
  - 遗留什么：[未完成/风险/接手提示]（或"无遗留"）。#标签
```

## 五、分类标签

条目尾部可带标签便于检索：`#feat #fix #docs #governance #incident #experiment #handover`。强制项：事故条目必带 `#incident` 并引用证据路径；实验条目必带 `#experiment` 并引用实验目录路径（如 `GOVERNANCE/experiments/24h-20260924/`）；交接条目必带 `#handover`。

## 六、正反例对照

### 6.1 反例：全要素缺失

`- 修了一些问题，系统更稳定了。`

无身份、无时间、无对象、无依据、无遗留，检索价值为零，复盘时无法归因。

### 6.2 正例：数据源降级（取材项目真实事件）

```markdown
- **[2026-09-20 15:40 (+08:00)] [工程-数据源] [常驻]**
  - 改了什么：降级数据源主链路：Tushare 返回 40101（token 失效）后切换为东财 API 拉取异动行情，Tushare 调用保留注释代码。
  - 为什么：token 失效且当日无新凭据可用，异动播报不能断流；依据：外部事件 40101 + 首屏永不空白约束（无数据时只剩演示卡不可接受）。
  - 遗留什么：恢复 Tushare 需新 token，凭据不落库不入文档；东财字段到 AlertFeed 契约的映射仅核对主字段，涨跌幅精度字段未核对——接手者若发现卡片数值精度异常，先查此映射。#fix
```

### 6.3 正例：云函数与端侧链路

```markdown
- **[2026-09-21 11:05 (+08:00)] [工程-云函数] [常驻]**
  - 改了什么：修改 generate-tts 重试逻辑：WebSocket 连接失败重试 2 次，间隔 3 秒。
  - 为什么：alerts.json 的 audioUrl 为 undefined 时端侧按需调 generate-tts，而百炼 TTS 仅支持 WebSocket，偶发握手失败导致卡片无语音；依据：已知问题清单。
  - 遗留什么：重试次数硬编码在函数内未配置化；如后续压测再参数化。#fix
```

### 6.4 正例：治理与交接

```markdown
- **[2026-09-23 22:30 (+08:00)] [治理-审计] [交接期] #handover**
  - 改了什么：新增 `GOVERNANCE/skills/governance/handover-protocol.md`，定义席位交接必读材料清单与阅读顺序。
  - 为什么：席位更替时知识依赖对话记忆，接手方上手慢且易漏红线；依据：治理总纲"文档优先于记忆"原则。
  - 遗留什么：KNOWN-ISSUES.md 条目编号体系尚未与 CHANGELOG 时间戳打通，跨文件检索暂靠全文搜索。
```

### 6.5 反例对照：WHY 缺失与遗留留空

```markdown
- **[2026-09-22 09:00 (+08:00)] [工程-端侧] [常驻]**
  - 改了什么：修改 Index.ets 轮询间隔。
  - 为什么：优化。
  - 遗留什么：
```

三处违规：依据缺失（为何改间隔？改到多少？影响什么？）、遗留留空、无标签。正确写法应写明动机（如降低请求压力）与依据（实验报告指标），遗留写明新间隔对数据实时性的影响。

## 七、写入前自查清单

1. 五要素是否齐全？无遗留时是否显式写了"无遗留"？
2. WHAT 是否含可定位的文件路径或对象名？
3. WHY 是否引用了可核查的依据？
4. 是否一条目只写一件事？
5. 是否夹带 Token/密钥原文？有则立即脱敏重写；
6. 时间戳与阶段标签是否符合第二章格式？
7. 事故/实验/交接类是否带强制标签并引用证据路径？
8. 若是更正条目，是否引用了原条目时间戳？

## 八、与其他技能的衔接

- learning-loop.md 的"结果记录"步骤以本规范条目为载体，条目质量决定闭环质量；
- handover-protocol.md 要求接手者倒序精读最近条目，五要素齐全是阅读效率的前提；
- 24h-autonomy.md 的准备期宣告、窗口小结落账与复盘总结，均按本规范追加；
- skill-doc-format.md 将"账本五要素齐全率"列为技能库健康度参考指标。

## 九、常见坏味道

1. 账本分叉：在模块目录另建局部 changelog，时间线断裂；
2. 追溯改写：偷偷修改旧条目，破坏审计可信度；
3. 批量打包：把"一次性提交 20 个文件的改动"写成一条，事后无法定位单一文件的变更动机；
4. 证据悬空：事故条目写"已修复"但无日志或截图路径佐证。

### 自我评估
- 正确性：4分 五要素定义、追加规则与正反例均取材项目真实事件（Tushare 40101、generate-tts 按需调用、交接技能新增），无事实杜撰；阶段标签枚举需随治理演进维护。
- 完整性：4分 覆盖位置、规则、要素、模板、标签、正反例、自查清单与技能衔接；未含自动化校验脚本设计。
- 可复用性：5分 模板可直接复制填写，正反例覆盖数据源、云函数、治理三类高频场景，自查清单可打勾执行。
