# 技能：闭环学习方法

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.0 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语）

## 一、定位与总览

闭环学习是治理体系把"做过的事"变成"可复用能力"的标准流程，五步依次为：

**结果记录 → 质量评估 → 模式识别 → 技能编写 → 复用（回流到记录）**

一句话定义每步：结果记录——把发生了什么以可核查形式落盘；质量评估——给产出与记录本身打三维分；模式识别——跨事件找重复，提炼可泛化规则；技能编写——把模式写成技能文档；复用——下个同类任务先查技能库，用后回填效果，回到第一步。

触发时机：每次任务完成、每次事故处置完毕、每次 24 小时实验复盘（见 24h-autonomy.md 第 3.4 节）、每次交接收尾（见 handover-protocol.md），都是一次循环的起点。循环不设终点：复用的效果本身成为下一轮记录素材，形成螺旋上升。

## 二、第一步：结果记录

### 2.1 载体（按优先级）

1. `GOVERNANCE/CHANGELOG.md`：一切变更与事件的时间线主账本，条目格式遵循 changelog-format.md 五要素；
2. 实验目录 `GOVERNANCE/experiments/24h-YYYYMMDD/`：实验类事件的 metrics.csv、incident.md、report.md；
3. `GOVERNANCE/KNOWN-ISSUES.md`：缺陷与现状登记。

### 2.2 最小记录单元（三件套）

现象（可核查证据：日志行、截图路径、接口返回码）、处置（改了哪个文件或配置）、结果（有效/无效/部分有效）。缺证据的现象一律降级为"待核实"，不得作为后续归纳依据。

## 三、第二步：质量评估

对刚完成的任务或处置评三维分（各 1-5）：

- 正确性：结论与改动是否与事实相符，有无把臆测当事实；
- 完整性：要求覆盖的点是否全覆盖（对照任务清单或实验指标表）；
- 可复用性：换一个会话或接手者，凭留下的材料能否复现同样结果。

评分纪律：分数必须附一句话简述并指向具体事实；正确性打 5 分须能通过"冷启动复现"想象测试（见 skill-doc-format.md 第四章）；任一维度 ≤2 分时，必须在 CHANGELOG 条目的"遗留什么"里登记改进动作，否则本次评估无效。

## 四、第三步：模式识别

跨记录找重复，操作步骤：

1. 聚簇：每周或每个实验复盘时，把近期 CHANGELOG 与 incident 记录按主题聚簇（数据源、TTS、推送、首屏、合规、治理流程）；
2. 判定：同簇同类事件 ≥2 次，才升级为候选模式；单次偶发（如一次网络抖动）只进 KNOWN-ISSUES，不成模式；
3. 表述：候选模式写成一条可泛化规则，句式固定——"当 X 条件出现时，应当 Y，因为 Z"；
4. 分类：区分工程模式（如外部依赖与预设不符时占位/降级保主链路）与治理模式（如记录缺失导致复盘失明）。

## 五、第四步：技能编写

按 skill-doc-format.md 六步流程把模式写成技能文档：

- 落盘位置：`GOVERNANCE/skills/<分类>/<主题>.md`；治理类入 skills/governance/；工程集成类可入 skills/integration/；
- 命名：主题式短横线命名，与既有五技能（24h-autonomy、changelog-format、skill-doc-format、learning-loop、handover-protocol）风格一致；
- 硬要求：过该规范第三章五门槛与冷启动验证；写完追加 CHANGELOG 条目并登记技能索引；
- 拒绝越级：只有第三步产出的候选模式才可成文，防止单次事件稀释技能库信噪比。

## 六、第五步：复用与回流

1. 先查后做：任务启动时先看技能索引 `GOVERNANCE/skills/README.md`，与本任务主题相关的技能必须先读再动手；
2. 失效即录：执行中发现技能误导或失效，当场记录（这就是新循环的第一步），复盘时修订技能并递增版本号；
3. 有效即注：执行有效，在收尾 CHANGELOG 条目的"为什么"里注明依据了哪个技能，便于统计命中率；
4. 回流成环：复用效果进入下一轮记录，循环回到评估环节，闭环不中断。

## 七、循环度量与健康度

| 指标 | 含义 | 健康值 |
|---|---|---|
| 记录率 | 事件具备三件套记录的比例 | 100% |
| 模式转化率 | 候选模式中最终成文技能的占比 | ≥50%（过低说明识别太滥） |
| 技能命中率 | 新任务启动时命中可复用技能的比例 | 逐季上升 |
| 技能失效率 | 复用时发现技能误导的比例 | ≤20%（过高说明工程演化快于文档，需集中修订） |
| 闭环周期 | 事件发生到技能成文的中位时长 | ≤2 周 |

度量数据来源即 CHANGELOG 与技能索引，无需另建系统；每月复盘时顺带核算一次即可。

## 八、项目实例走查（Tushare 40101 降级东财）

用一次真实事件走完五步，作为执行模板：

1. 结果记录：CHANGELOG 追加条目（工程-数据源，降级动作，依据 40101），KNOWN-ISSUES 登记凭据失效；
2. 质量评估：核对降级后 FEED 数据满足 AlertFeed 契约、卡片流不空白——正确性 4（涨跌幅精度字段未核对）、完整性 4、可复用性 4，简述须指向具体字段；
3. 模式识别：与"百炼 TTS 仅支持 WebSocket""broadcast-a2a 推送需换华为 Push Kit REST""PushService.ets 占位封装待 AGC 配置"聚簇，得到候选模式："当外部依赖与预设不符或不可用时，应当先占位/降级保住主链路与三底线，因为用户侧服务连续性优先于后端完美性"；
4. 技能编写：该模式可沉淀为"外部依赖降级预案"技能（规划中，拟落盘 `GOVERNANCE/skills/integration/degradation-playbook.md`，成文前在本文档标注"规划中"）；
5. 复用：下次接入新外部依赖（如华为 Push Kit REST 落地）时，先读该技能再动手，处置完毕回填效果，开启下一轮循环。

## 九、反模式

1. 只记录不评估：账本很厚但没有分数与简述，复盘无从下手；
2. 越级归纳：单次事件直接写成技能，稀释信噪比；
3. 技能僵尸化：写完从不复用、从不修订，命中率永远为零；
4. 循环断裂在回流：任务开始不查技能库，闭环退化为单向流水账；
5. 模式句式失守：候选模式写成叙事散文而非"当 X 应当 Y 因为 Z"，无法直接转化为技能的规则段。

### 自我评估
- 正确性：4分 五步定义、判定规则与实例走查均取自项目真实事件链（40101 降级、WebSocket 限制、Push Kit 待换、PushService 占位），无虚构；健康度阈值为经验建议值。
- 完整性：4分 覆盖五步、载体、评分纪律、度量与反模式；未含跨项目迁移指引与多人并行场景。
- 可复用性：5分 每步给出载体路径、固定句式与实例对照，新席位可即时上手执行。
- 字数：约3000字
- 使用模型：GLM-5.3-Flash
