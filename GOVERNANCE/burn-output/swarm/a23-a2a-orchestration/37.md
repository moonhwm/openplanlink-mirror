# 停机条件与收敛

## 一、蜂群何时停下

蜂群黑板没有天然的终点:知识源总还能再写点什么、再补一个假设、再消解一个矛盾。停机条件决定黑板何时宣布"够了"。它必须回答两个问题:足够好(质量维)与到此为止(成本维)。只有成本维的黑板会戛然而止留下烂尾楼,只有质量维的黑板会无限打磨烧穿预算——收敛设计就是把两维写成可判定的谓词组。

## 二、四类停机谓词

```text
1. 达标停机:  结论层覆盖全部核心子问题, 且无未消解的
              阻断级 conflict, 且关键结论置信度 >= 阈值
2. 饱和停机:  连续 M 代无有效新增(新条目均为重复或
              被立即取代), 知识源群体已无增量可写
3. 预算停机:  总代数/总成本/墙钟任一触顶
4. 活性停机:  连续 K 代 ready 队列为空, 无人可触发
```

达标是唯一的质量出口;饱和与活性是"自然熄火"信号,通常意味着知识源能力对当前任务已榨干;预算是最后的硬闸。四者优先级从上到下,任何时刻第一个为真者生效。

## 三、收敛的度量:让"接近完成"可观测

停机判定的质量取决于中间进度的可观测性。推荐维护一个覆盖度向量:每个核心子问题标注状态(空白/有证据/有假设/有结论/结论已锁定),覆盖度 = 已锁定占比。调度优先级向未覆盖子问题倾斜,停机判定检查覆盖度与置信。进度的可视化不是装饰——它让"还差多少"成为运维问答,而非玄学猜测。

## 四、收尾模式:从发散到收缩

接近停机时应主动切换收尾模式,而非等预算强行截断:

```python
def mode(bb, budget) -> Mode:
    if bb.coverage_locked >= 0.95 and not bb.blocking_conflicts:
        return FINALIZE          # 全收束
    if budget.remaining < 0.15:
        return FINALIZE          # 预算尾声,强制收束
    if bb.stagnation_gens >= M:
        return WRAP_UP           # 饱和,整理收尾
    return EXPLORE               # 正常探索
```

FINALIZE 模式下只放行收束类知识源:缺口标注(把没解决的诚实标出)、置信复核、结论整理;EXPLORE 模式正常调度。模式切换本身写入黑板日志,事后分析停机质量时,能区分"从容收尾"与"仓促截断"。

## 五、带保留意见的交付

非达标停机(饱和/预算/活性触发)的交付必须诚实:结论层照常输出,同时生成保留意见清单——未覆盖子问题、未消解矛盾、低置信结论及其原因。保留意见不是失败报告,是黑板给下游的风险披露。下游(用户或后续流程)有权基于披露决定接受、降级使用或升级人工,把"半成品"伪装成"完成品"是停机设计里唯一不可原谅的错误。

## 六、防早停与防拖尾

两方向的失调各有解法:早停(覆盖度虚高,子问题标记锁定但证据薄弱)靠锁定审计——结论锁定动作要求引用证据链,审计抽样复核锁定质量;拖尾(最后一两个子问题反复补不齐,预算持续空烧)靠子问题止损——单个子问题设独立预算,超时即标记"尽力而为"进入保留意见,不再无限投入。

## 七、收敛统计与调参

停机参数(阈值、M、K)的调校依据收敛统计:停机原因分布(达标占比是体系健康度第一指标,持续低于一半说明知识源能力或覆盖度设计有问题)、收尾模式进入时的覆盖度分布、保留意见的消化率(下游实际接受了多少非达标交付)。三者按月复盘,停机条件从静态配置进化为随任务画像自适应的策略,黑板的运行经济学才真正闭环。
