# 争议升级机制

## 一、升级是体系的泄压与纠错通道

争议升级(escalation)指下层无法终局的争议,按预定通道交给更高裁决层处理的机制。它同时承担两个看似矛盾的职能:泄压——让僵局不堵塞自动化流程;纠错——让下层错误有机会被上层发现并翻案。没有升级通道的系统,僵局要么被强制机械裁决(埋雷),要么无限重试(烧钱);升级通道泛滥的系统,则把自动化退化成人盯人。

## 二、升级触发的分类

触发升级的信号分四类,每类绑定不同的升级理由字段:

```text
低置信触发:  裁判置信度 low -> 升级人工复核
合议僵局:    表决未达门槛 -> 升级更高合议层或仲裁席
规则冲突:    两条标准条款同时适用且结论相反 -> 升级规则维护方
越权请求:    争议标的超出本级权限(如金额/风险等级) -> 强制升级
```

理由字段不是注释,是上级分诊的依据:低置信走复核队列,规则冲突走标准修订流程,两类处理者完全不同。

## 三、升级路径的层级设计

典型四层,层间窄接口:

1. **规则层**:无语义争议,阈值判定,零成本;
2. **自动裁判层**:模型独任/合议,处理语义争议;
3. **专家层**:人工复核,处理低置信与僵局,按领域分诊;
4. **治理层**:标准与判例的修订者,处理规则冲突与系统性问题。

关键设计是"跃层禁止":每级只能升到紧邻上级,防止任何人把琐事直接甩给顶层;同时"降级沉淀"必须存在:专家层的裁决结论定期被治理层提炼成判例或规则,回填下层,让同类争议未来不再升级——升级机制的健康度不看升级量,看每条升级最终沉淀了多少自动处理能力。

## 四、升级件的封装

升级时传给上级的必须是一份完整的争议档案,而非一句"处理不了":

```python
@dataclass
class Escalation:
    origin: str              # 来源层级与案件标识
    reason: str              # low_confidence | deadlock | rule_conflict | ...
    dispute: Dispute         # 原始争议件
    attempts: list[Verdict]  # 已有裁决尝试与依据
    deadline: float          # 期望处理时限
    suggestion: str          # 下层的倾向性建议(仅供参照)
```

`attempts` 字段让上级不必从零开始——下层已排除的选项、已否定的依据都在档。`suggestion` 保留下层建议但标注"仅供参照",既利用一线信息,又防止锚定。

## 五、人工层的成本护栏

专家层是整条链最贵的资源,护栏三件套:升级率预算(单日升级量上限,超限自动转为排队并告警系统设计问题);升级件分级(SLA 按风险分级,琐碎件批量处理,重大件即时);决策记录强制(人工必须填写结构化裁决书,不允许"电话口头拍板"不留档——那会让沉淀链条断裂)。

## 六、升级的统计与回路

升级数据是体系改进的富矿,三个必看统计:升级原因分布(哪类触发占大头,对应哪层能力短板)、升级翻转率(上级推翻下层的比例,过高说明下层裁判校准失效)、重复升级率(同类争议反复升级,说明沉淀回填失灵)。每月把这三组数据摆在一起,体系的改进优先级自己会浮出来:先修翻转率高的层,再补沉淀回路,最后才谈扩容人工。
