# 黑板数据结构设计

## 一、数据结构决定协作上限

黑板是蜂群模式的"宪法+国库":它规定了什么可以写、写在哪、谁能读。结构设计松散,知识源之间无法建立精确的触发与依赖;结构设计僵化,新知识源难以插入,黑板失去扩展性。设计目标是在"机器可判读"与"演化可扩展"之间取得平衡,核心手段是分层加带模式的数据条目。

## 二、数据条目的参考模式

黑板上的最小写入单位是条目(entry),推荐结构:

```python
@dataclass
class Entry:
    entry_id: str        # 全局唯一
    layer: str           # 所属层次:L0..L4
    kind: str            # 条目类型:fact|hypothsis|conflict|gap|conclusion
    payload: dict        # 类型化的内容,按 kind 有独立 schema
    provenance: dict     # 来源:哪个KS、依据哪些entry_id、外部引用
    confidence: float    # 置信度,写入方给出
    superseded_by: str | None  # 被新条目取代的指针(黑板不删数据)
    ts: float

class Blackboard:
    def append(self, e: Entry) -> None:
        self._validate_schema(e)          # 按kind校验
        self._check_permission(e)         # 写入层权限
        self._check_arity(e)              # 依赖条目存在且未失效
        self.entries[e.entry_id] = e
        self._notify(e)                   # 触发订阅者
```

两个字段承担了黑板的大部分秩序:provenance 让任何条目可回溯到依据链,构成黑板上的证据图;superseded_by 实现"追加不改写"——修正通过新条目加取代指针完成,历史永远在档,震荡与回滚因此可检测。

## 三、分层 schema 与条目类型

每层定义允许的条目类型与其 schema:

- **事实层**:fact 条目,payload 必须含断言、原文摘录、外部来源定位;
- **假设层**:hypothesis 条目,必须声明它解释哪些事实、与哪些事实冲突;
- **结构层**:conflict(矛盾对,指向两条互斥条目)与 gap(缺口,声明缺什么);
- **结论层**:conclusion 条目,必须引用其立足的假设与事实集合。

类型化让触发谓词写得精确("存在 conflict 且其两侧 confidence 差小于 0.2"是明确的可计算条件),也让越层违规在写入时被 schema 拦下。

## 四、读取视图与订阅

知识源不应直接遍历黑板,通过视图按需读取:

```text
快照视图:   返回指定层的条目快照,触发谓词只用此视图,幂等
增量视图:   返回自上次读取以来的新增条目,订阅处理用
证据图视图: 以某条目为根,展开完整 provenance 子图,复核用
```

快照视图保证触发判断的纯函数性(同一黑板状态总是同一判断),这是调度可复现的前提;增量视图避免轮询全量;证据图视图给裁判与审计使用。

## 五、黑板的持久化与恢复

黑板是长任务的全部记忆,必须当持久化状态而非内存对象对待:条目追加即落盘(或按代批量落盘);进程崩溃后从最后一致代恢复,未完成的知识源执行作废重放;黑板可整体导出为可读文档,这是黑板相对消息传递架构的天然优势——状态集中可见,可解释性唾手可得。

## 六、容量与修剪

长跑黑板会膨胀,修剪规则:被取代超过 N 代且无活跃引用的条目归档冷存;gap 条目解决后转入已决区;归档不删除 provenance 引用,引用冷存条目时按需加载。修剪必须保留黑板的可解释性主干——任何在档结论仍能展开完整证据链,修剪只处理冗余中间态。

## 七、设计验收

黑板结构是否合格的三条验收:新增一种知识源不需要改动黑板结构代码(扩展性);任一结论条目可展开完整证据子图(可追溯性);同一初始状态重放,条目追加序列的层次依赖关系始终合法(秩序性)。三条达标,黑板才配得上"协作基础设施"的名字。
