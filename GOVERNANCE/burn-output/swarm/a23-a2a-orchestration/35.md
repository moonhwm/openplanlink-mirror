# 订阅与通知机制

## 一、从轮询到订阅

知识源需要知道黑板何时出现自己关心的变化。最朴素的方案是轮询:每个知识源周期性读取黑板快照求值触发谓词。轮询的代价随知识源数量与黑板规模相乘增长,且大量求值注定为假。订阅机制反转控制:黑板在状态变化时主动通知相关订阅者,知识源只在被通知后才做精确的触发判定。这是黑板能否扩展到中大规模的第一道工程关。

## 二、订阅声明的层级

订阅粒度分三级,按需选用:

```text
层订阅:    感知某层的任何新条目(粗,适合宽兴趣的知识源)
类型订阅:  感知某层某kind的新条目(中,最常用)
模式订阅:  感知匹配特定模式的条目(如 conflict 且
          两侧confidence差<0.2)(细,精确但需匹配引擎)
```

粒度选择的原则:通知只是"可能相关"的信号,精确判定永远由知识源的触发谓词完成。宁可订阅粗一点多收几次无效通知,也不要把复杂的模式匹配塞进通知层——那会让通知路径变成第二个需要调试的复杂系统。

## 三、通知的投递语义

黑板通知必须明确三种语义并写入契约:

1. **至少一次投递**:知识源可能收到同一事件的重复通知,触发判定是幂等的纯函数,重复求值无害;
2. **合并投递**:知识源忙于执行时,期间积累的多条通知合并为一次唤醒,唤醒后读最新快照——错过中间态没有关系,触发判定只关心当前态;
3. **无序容忍**:通知不保证顺序,依赖顺序的逻辑(如"必须先看到事实再看到假设")应该表达为触发谓词对快照的检查,而非对通知顺序的信任。

## 四、参考实现骨架

```python
class Blackboard:
    def _notify(self, entry: Entry):
        subs = self._index.match(entry.layer, entry.kind)
        for ks_id in subs:
            self._wakeups.mark(ks_id)     # 只做标记

class Scheduler:
    def on_cycle(self):
        woken = self._wakeups.drain()      # 合并唤醒
        for ks_id in woken:
            ks = self.registry[ks_id]
            if ks.trigger(self.bb.snapshot(ks.reads)):
                self.ready.add(ks_id)
```

关键在 `mark` 与 `drain` 的分离:黑板侧只做廉价的标记,执行侧在调度周期统一排空——通知路径上没有任何模型调用或重计算,黑板写入的延迟不受订阅者数量影响。

## 五、死信与滞后

两类通知异常要有专门处理:死信(知识源连续多次唤醒但触发判定恒为假,说明订阅声明与触发谓词不匹配,是配置缺陷,应告警提示修正订阅);滞后(通知积压队列持续增长,说明知识源消化速度跟不上黑板更新速度,应降低其订阅粒度或提示调度降低相关层位的更新频率)。

## 六、跨进程黑板的通知

黑板分布到多进程时,通知经由消息总线传播,此时必须处理:通知与黑板状态的竞态(收到通知时快照可能已又变化——合并投递语义天然容忍这一点);通知丢失(总线至少一次语义加知识源的周期性对账唤醒兜底:即使无通知,每小时全量判定一次触发,防漏);风暴抑制(某一层短时间高频写入时,通知按层聚合成节拍通知,避免唤醒风暴)。

## 七、验收

订阅机制的健康指标:无效唤醒率(唤醒后触发判定为假的比例,持续高于一半说明订阅粒度过粗)、平均唤醒到判定延迟、死信计数。订阅系统的验收测试:注入合成条目序列,断言每个相关知识源恰好被唤醒(至少一次语义)且触发判定结果与直接轮询完全一致——订阅层绝不改变语义,只改变效率,这是它存在的全部理由。
