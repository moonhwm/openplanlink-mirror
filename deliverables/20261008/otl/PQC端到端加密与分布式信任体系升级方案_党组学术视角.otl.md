## 1. 算法选型

### 1.1 选型总表

### 1.2 HMAC-SHA3-512 树：为什么是「树」

三个同构面共用 SHA3-512：

1. **消息面**——签名计算式（唯一权威口径）：`sig = HMAC_SHA3_512(key_bytes, UTF8(seat + text)).hexdigest() 前 32 位（小写）`；seat 绑进原文，换席名重放他人签名必然验签失败；text 取原始请求体字节（桥侧须在 `JSON.parse` 之前读 raw body），保证对字节级篡改敏感；验签用常量时间比较防时序侧信道。
   批注：引用 BRIDGE_HMAC_SPEC.md §1.2「签名计算式」与 §1.3「校验规则」；席位侧参考实现 `burn/scripts/bus_auth.py:83-95`（已 py_compile + 自含自测通过，SPEC 头部载明）。
2. **身份面**——`X-Seat-Id` 取席位哈希树 `identity_id`（本席现用 `moon@zcode`），身份根为 SHA3 Merkle 根（本席 root a69ccb57…）。
   批注：引用 BRIDGE_HMAC_SPEC.md §1.1 表格 X-Seat-Id 行（其注引 `burn/a2a/board_session_20260927.md:146`）；SECURITY_MASTER_REPORT §二处置建议 #2「SHA3 证明链：身份根（Merkle）已具备」。
3. **审计面**——台账叶哈希与 Merkle 根同用 SHA3-512（§7）。

**截断口径统一**：指纹与签名均取 hexdigest 前 32 位，与治理索引指纹口径一致。
批注：引用 BRIDGE_HMAC_SPEC.md §1.2 末条「取 hexdigest 前 32 位与治理索引指纹口径一致（`burn/governance/INDEX.md:3`）」。

**如实局限（不得超范围宣称）**：现行签名不防重放（原文不含时间戳）；总线为 http 明文（P2 挂账，需桥侧证书）；共享密钥模型下桥即信任根（桥读得到全部席 key）；密钥缺位时降级不附头。v2 路线：`X-Seat-Ts` 入原文（`seat+ts+text`）+ 24h 窗口对齐 COMMS 时效层；SHA3 证明链 `seat@root` proof。
批注：引用 BRIDGE_HMAC_SPEC.md §6「已知局限」四条与 v2 路线注记。

### 1.3 AES-256-GCM

- 用途：L4 载荷加密（§3），每消息唯一 12 字节随机 nonce，nonce 随密文传输（GCM 标准做法；nonce 重用对 GCM 是灾难性失效，故 nonce 唯一性入验收指标）。
- 与 HMAC 的分工：GCM 认证标签保护密文完整性；X-Seat-Sig 保护**整个请求体字节**（含密文与信封头）并承载发送方身份——两层不互相替代：外层签名回答「谁发的、body 未被改」，内层 GCM 回答「载荷对非持钥者不可读且不可伪造」。
- 本机已具备实现：`cryptography 50.0.1`（实测在位，见 §4）。

### 1.4 标识密码（IBC）与国密路线

- IBC 的适配性论证：本网络席位标识（identity_id）天然稳定且全网唯一，符合 IBC「标识即公钥」的前提；相比 PKI，免除跨席证书签发/吊销/续期链，与「桥侧 seat→key 表」的现有治理面同构——IBC 可视为该表从「对称共享密钥」升级为「非对称标识派生密钥」的自然延伸，同时消解 §1.2 局限 3（桥不再必然读得到全部席私钥，信任根收敛到 KGC 私钥）。
- **SM9**：已发布标识密码算法国标（主权人术语照录）。工程注记：SM9 双线性对运算开销显著高于对称原语，具体量级**待实测**（本机无 SM9 实现库，见 §4.3 探测记录）；标准号与参数集**以正式发布文本为准**。
- **SM10**：**以国家密码管理局正式发布文本为准，本席未核验其公开标准号**——本稿不对其算法形态、适用场景作任何断言，仅列观察位；若正式发布文本出台且适配本网络，按修订流程增补。
- **ZUC**：序列密码算法。工程注记：序列密码的适用面是比特流/流式信道（移动通信加密为其标准场景），本网络消息面为离散 JSON-RPC 报文，更适配分组/AEAD 形态（AES-256-GCM 或国密对应 AEAD）；ZUC 在本体系中的位置是**流式通道储备**（如未来 WebSocket 长连接面，.env 已备 DASHSCOPE_WS_KEY/DASHSCOPE_WS_BASE 键名位），非当前主线。标准号**以正式发布文本为准**。

### 1.5 QRNG 熵源增强

- 目标态：L0 根密钥生成与 L1 派生种子由 QRNG 输出播种；L4 nonce 熵池可由 QRNG 持续补充（GCM nonce 只需唯一性与不可预测性，CSPRNG 已足，QRNG 为增强项非必需项——如实区分）。
- 过渡态（现状）：Python `secrets`（`os.urandom` 后端，OS CSPRNG）。BRIDGE_HMAC_SPEC §3 密钥生成口径即 `secrets.token_hex(32)`，本稿沿用。
  批注：引用 BRIDGE_HMAC_SPEC.md §3「① 生成」行。
- QRNG 设备选型、计量认证与随机性检测标准（如 GM/T 相关随机性检测规范）**以正式发布文本为准**，硬件注入走审批链（§10 候终审清单）。

## 2. 后量子迁移

### 2.1 威胁模型与迁移必要性

- 「先收割、后解密」（harvest-now-decrypt-later）：攻击者今日截获密文（本网络 http 明文面使截获成本为零——P2 挂账事实），待量子计算机可用时解密。**对长寿命敏感数据，该风险现在就成立**，与量子机何时问世无关。
  批注：http 明文面事实引用 BRIDGE_HMAC_SPEC.md §6-2 与 SECURITY_MASTER_REPORT.md §三 P2 清单「总线明文 http」。
- 受威胁原语：RSA/ECC 系公钥算法（Shor 算法）。对称原语（AES-256、HMAC-SHA3-512）受 Grover 类加速影响为平方根级——AES-256 后量子安全余量 128 bit、SHA3-512/HMAC 截断 128 bit 口径同理，**本稿的对称面选型在后量子时代无需更换**，需要迁移的是公钥面（密钥协商与数字签名）。

### 2.2 双栈并存：NIST PQC × 国密

| 栈 | 密钥封装/协商 | 签名 | 备份签名 |
|---|---|---|---|
| NIST PQC | **ML-KEM**（FIPS 203，格基，源自 CRYSTALS-Kyber） | **ML-DSA**（FIPS 204，格基，源自 CRYSTALS-Dilithium） | **SLH-DSA**（FIPS 205，哈希系，源自 SPHINCS+，保守假设最少） |
| 国密 | SM9 标识密码（密钥封装/加密/交换）+ SM2 类椭圆曲线（量子威胁下面临同等风险，仅作存量兼容位） | SM9 签名 / SM2 签名（同前注） | —（国密侧哈希系备份签名路线以国家密码管理局正式发布文本为准） |

- FIPS 203/204/205 已由 NIST 于 2024 年 8 月正式发布（版本号、参数集与字节长**以正式发布文本为准**）。
- **双栈含义**：两栈并行在册、以算法标识符协商选择，任一栈单点失效不致全网密码面瘫痪；跨栈不混用单一原语（禁止「SM9 协商 + ML-DSA 签名」这类未经分析的拼接，除非有成文安全论证）。

### 2.3 混合密钥协商（过渡形态）

- 形态：**X25519 + ML-KEM 混合 KEM**——双方各跑经典与 PQC 两条 KEM，共享密钥 = KDF(K_classic ‖ K_pqc, 上下文标签)。安全下界：两条 KEM **任一未被攻破**则会话密钥保密（保守并集假设），这是 IETF 混合设计讨论的主流立场（draft 编号与最终文本**以正式发布文本为准**）。
- 在本网络的落点：L2 会话密钥派生（§3）在 PQC 库注入后由「单方 KDF 派生」升级为「混合 KEM 协商 + KDF」；升级前 L2 维持现口径。
- **信封预算约束（本网络特有，必须先算账）**：总线单条 8000 字符硬上限（实测 8001 字符硬拒）。
  批注：引用 SECURITY_MASTER_REPORT.md §三「总线面 7 条」之「8001 字符硬拒」实测记录。
  ML-KEM-768 密文约 1088 字节、ML-DSA-65 签名约 3300 字节量级（**以 FIPS 正式发布文本为准**），base64 后各膨胀约 4/3——PQC 签名**放不进现有 32-hex 头口径**，工程路径三选一：① 签名对象改为 SHA3-512 摘要、签名体走消息体分段；② 签名字段带外传输（回执/台账锚定）；③ 仅在 epoch 边界以 PQC 签名锚定 Merkle 根（低频、可容忍大字段），逐消息维持 HMAC。本稿推荐 ③+① 组合：逐消息热路径零膨胀，信任锚低频加固。膨胀核算与实测**待实测**。

### 2.4 经典算法退役判据（判据，非日期承诺）

本稿**不给出任何退役日期**。经典公钥算法（及其在本网络的一切使用位）退役当且仅当以下五条**全部**成立：

1. **实现合规判据**：PQC 双栈实现通过商用密码应用安全性评估或同等权威认证（§9），认证范围覆盖本网络实际部署形态；
2. **覆盖判据**：全网在册席位 100% 完成双栈改造，混合握手覆盖率连续 ≥90 天为 100% 且零降级事件（测法：桥侧 auth 日志算法标识列 + 审计局对账单新增「未升级席」列，承 SPEC §4 灰度对账机制）；
3. **政策判据**：NIST / 国家密码管理局权威政策明确经典算法退役时间表且该政策对部署方生效（政策文本**以正式发布文本为准**）；
4. **性能与预算判据**：§4 性能表中全部「待实测」项落账且满足验收指标（含 8000 字符信封预算核算）；
5. **主权判据**：主权人终审裁定退役。

任一判据不成立即不退役；判据成立顺序不作预设。**HMAC-SHA3-512 与 AES-256-GCM 不在退役射程内**（§2.1 对称面结论），其轮换属密钥管理（§3）而非算法退役。

## 3. 分层密钥派生与动态轮换

### 3.1 五层密钥体系

```
L0 根密钥        HSM/离线冷介质 · QRNG 播种（过渡态 CSPRNG）· 不出界，仅导出派生服务
  └─ KDF(域分隔标签 "L1|seat|epoch") ──►
L1 席位身份密钥   每席一枚 · 与身份哈希树 identity_id 绑定（SHA3 root 指纹在册：本席 a69ccb57…）
  └─ KDF("L2|session|ctx") ──►        （PQC 注入后此级升级为混合 KEM 协商，§2.3）
L2 会话密钥       每会话/每 epoch 一枚 · 不落盘（内存态）或短期密封落盘
  └─ KDF("L3|auth|msg_class") ──►
L3 消息认证密钥   HMAC-SHA3-512 用钥 · 即现行 BUS_HMAC_KEY 形态的派生化升级
  └─ KDF("L4|enc|kv") ──►
L4 数据加密密钥   AES-256-GCM 用钥 · 每消息唯一 12B nonce · kv 版本标签随行
```

- KDF 工程口径：以 HMAC-SHA3-512 为核的 HKDF 构造（extract-then-expand），域分隔标签逐级硬编码，禁止跨级复用同一密钥材料。注：HKDF 的 RFC 口径以 HMAC 为核，本网络实例化选 HMAC-SHA3-512 属工程选型，其安全论证沿用 HKDF 通用论证 + SHA3 族性质；正式标准号引用**以正式发布文本为准**。
- 层级不变量：**下层密钥永不反推上层**（KDF 单向）；**L0  compromise 即全网换根**（等同身份重铸，走审批链）；L1 轮换 = 席位身份重发事件（身份树需同步更新并 Merkle 重新锚定）；L2-L4 轮换为常规运维事件。

### 3.2 与 5h 通道窗对齐的可行性论证

**事实前提**：5h 窗是**额度窗**（撞墙码 1308；周墙 1310；start-plan 墙 1005——遇墙零重试纪律），不是密码窗。
批注：引用 AGENTS.md「硬纪律」章「撞墙即停」条与「运行入口」`auto_reset_5h.py` 口径。

**论证**（分层给结论，不一刀切）：

1. **L2/L3 对齐 5h 窗：可行且推荐**。取 `epoch = floor(unix_ts / 18000)`，以额度窗边界为密钥 epoch 计数器锚点——与 `auto_reset_5h` 重置节律、审计对账单时间粒度天然对齐；派生纯软件 KDF、无握手状态，成本为每 epoch 一次哈希运算（微秒级，§4 实测口径外推——KDF 即若干次 HMAC-SHA3-512，单次 15.9µs@1KB 量级已实测）。HMAC 无握手状态、改钥即生效的性质（SPEC §3 轮换条已论证）同样适用于 KDF 派生密钥：新旧 epoch 交接期内桥侧按 kv 双读即可，无需在线协商。
2. **L4 对齐粒度：每消息**（nonce 唯一性天然逐消息）；L4 密钥本身随 kv 按 epoch 或按 30 天常规周期轮换（承 SPEC §3「常规 30 天一换」纪律）。
3. **L0/L1 对齐 5h 窗：不可行且不必要**。HSM/离线操作成本高；身份根必须稳定，否则身份哈希树、Merkle 审计锚、跨席信任全部失去连续性。L1 轮换只由事件触发（疑泄露、席位重铸）。
4. **红线**：**安全轮换不得等待额度窗**。额度墙是资源约束不是安全约束——疑泄露立即全席换钥（承 SPEC §3「疑泄露立即全席换钥；共享密钥模型下单点泄露即全席伪冒面」），该事件驱动通道独立于 5h/30 天一切时间驱动通道，且换钥操作走 `.env` 投放不经总线（明文禁令）。

**结论**：5h 窗作为 L2/L3 的 epoch 锚点是运维便利与对账粒度的双赢，予以采纳；作为 L0/L1 轮换周期予以否决；作为安全事件的门槛予以禁止。

### 3.3 密钥版本管理（kv 标签）与历史数据平滑迁移

- **kv 标签**：信封在现行 v4 四元标签（priority/ttl/delivery/reply_to）旁**增列** `kv`（key version，取值 = epoch 计数或语义版本号，协议评审定稿）。缺省语义：无 `kv` = 历史版本（桥侧查兼容表按旧钥验签/解密），保证向后兼容、历史行为逐字节不变（承 SPEC §6-4 密钥缺位降级的兼容性设计哲学）。
  批注：v4 四元标签口径引用 AGENTS.md「A2A 网络」章「消息：v4 四元标签（priority/ttl/delivery/reply_to）+ kind 三平面（hb./biz./esc.*）」。
- **桥侧 seat→key 表版本化**：表由 `seat → key` 升级为 `seat → {kv → key}`，旧版本条目只读保留（供历史消息验签/解密），删除权归主权人终审（承归档目录删除权口径）。
- **历史数据平滑迁移四则**：
  1. **宽限期双读**：新旧 kv 并行受理，宽限期时长候主权人裁定（§10 候终审清单）；宽限期满旧 kv 转只读存档。
  2. **HMAC 类历史消息不重签**：验签一律以发送时刻 kv 对应密钥执行——append-only 台账语义不因换钥而改变，历史对账可永久重跑复现（承 AGENTS.md「台账 append-only：对账单可重跑复现」）。
  3. **AES-GCM 类历史密文默认不重加密**：旧版 L4 密钥密封归档（冷介质 + SHA3-512 指纹登记 MANIFEST）；仅当某版本密钥确认泄露时对该版本密文强制重加密（事件驱动，范围可经 kv 标签精确定位——这是 kv 的核心审计价值）。
  4. **指纹链不动**：台账行与治理文档不承载密钥材料，密钥迁移不改变任何历史 SHA3-512 指纹与 Merkle 根；迁移事件本身以新台账行入账（esc.trace 纪律）。

## 4. 性能口径

### 4.1 目标口径（主权人原话照录）

「**签名验证延迟控制在毫秒级**」。

### 4.2 可实测方法与本机实测步骤

**测法口径**（python hashlib/hmac 计时脚本）：`time.perf_counter()` 包裹、N=20000 次迭代取均值、报告 µs/op；验签口径 = 重算期望签名 + `hmac.compare_digest` 常量时间比较（与 SPEC §1.3 校验规则一致）；AES-GCM 加密计时**含** 12B 随机 nonce 生成（`secrets.token_bytes(12)`），即工程真实路径。脚本全文（可重跑复现）：

```python
# pqc_bench_20261008.py 口径（本席 2026-10-08 实跑）
import hashlib, hmac, time, secrets
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
key = secrets.token_hex(32).encode(); seat = "moon@zcode"
for size in (1024, 8000):                       # 8000 = 总线字符硬上限口径
    msg = (seat + "x" * size).encode("utf-8")
    N = 20000
    t0 = time.perf_counter()
    for _ in range(N): sig = hmac.new(key, msg, hashlib.sha3_512).hexdigest()[:32]
    t1 = time.perf_counter()
    for _ in range(N):
        exp = hmac.new(key, msg, hashlib.sha3_512).hexdigest()[:32]
        hmac.compare_digest(exp, sig)           # 验签 = 重算 + 常量时间比较
    t2 = time.perf_counter()
    # AES-256-GCM：encrypt 含 secrets.token_bytes(12) nonce 生成
```

**本机实测结果（2026-10-08，Python 3.12.10，Windows-11-10.0.26340-SP0，本席工作站，N=20000）**：

| 操作 | 1KB 载荷 | 8000B 载荷（总线上限） |
|---|---|---|
| HMAC-SHA3-512 签名 | **15.9 µs/op（实测）** | **58.5 µs/op（实测）** |
| HMAC-SHA3-512 验签（重算+常量时间比较） | **12.7 µs/op（实测）** | **81.8 µs/op（实测）** |
| SHA3-512 纯哈希 | — | **52.8 µs/op（实测）** |
| AES-256-GCM 加密（含 nonce 生成，cryptography 50.0.1） | **6.0 µs/op（实测）** | **7.6 µs/op（实测）** |
| AES-256-GCM 解密 | **2.6 µs/op（实测）** | **5.3 µs/op（实测）** |

**结论（限定口径内）**：对称面（HMAC-SHA3-512 / AES-256-GCM）单操作为**微秒级**，对「毫秒级」目标留有 1-2 个数量级余量——**在纯算法开销口径内，毫秒级目标已达成（实测）**。但以下开销**不在**上表内，端到端延迟结论不得由上表外推：HTTP 往返、JSON 解析、桥侧中间件与 seat→key 查表、KDF 派生链多级开销、跨进程时钟偏差。端到端延迟**待实测**。

## 5. 细粒度属性基加密（ABE）按需授权

### 5.1 属性模型

- **属性三维**：`席位`（identity_id，如 moon@zcode）× `密级`（消息 priority 标签升格为密级维度）× `域`（kind 三平面 hb./biz./esc.*）。
  批注：三维的载体全部为现行信封既有字段，引用 AGENTS.md「A2A 网络」章 v4 四元标签 + kind 三平面口径。
- **目标语义**：密文侧绑定访问策略（如「esc.* 域 ∧ 密级≥L3 → 仅审计局席位与主权人可解」），解密密钥由属性权威（AA）按属性集签发——授权从「桥侧路由纪律」下沉为「密码学强制」，未授权者即便截获密文（http 明文面，§2.1）亦不可读。

### 5.2 第三方依赖现状（如实）

ABE 需配对密码/格密码第三方库（OpenABE、charm-crypto 类，或国密 SM9 标识密码实现库）。**本机 2026-10-08 实测：oabe / charm / petrelic / pyrelic / ibe / sm9 / gmssl 七库全部 ABSENT**（§4.3 探测实录）。依赖注入走审批链（涉资源：责任席提案→筹备组审议→主权人拍板，承 AGENTS.md「审批链」条），注入前本稿**不承诺 ABE 上线时间**。

### 5.3 过渡近似：白名单 + HMAC 双层（当前先行）

| 层 | 机制 | 达到的访问控制 | 达不到 |
|---|---|---|---|
| 第一层 白名单 | 桥侧 seat→key 表：`X-Seat-Id` 不在表 → 判 `none`（未注册席位不冒充已签身份） | 具名席位级准入、未签名消息可点名（对账单「未签名消息」列） | 密文级绑定——白名单管「谁能发」，不管「谁能读」 |
| 第二层 HMAC | X-Seat-Sig 持钥证明（名字不再是证据、密钥才是） | 发送方身份不可否认面（灰度转 strict 后强制） | 同上；且 http 明文面下载荷对旁路窃听者仍可读 |

批注：双层机制全部引用 BRIDGE_HMAC_SPEC.md §1.3 校验规则、§2 auth 日志、§4 灰度表；「名字不再是证据、密钥才是」引自 SPEC §5 COMMS 章程对应行；「未签名消息列」引自 SPEC §4 阶段 A 判据（与总报告处置建议 #3 合流）。

**定性（不夸大）**：双层近似是 ABE 的**发送侧准入近似**，不是其**接收侧密文授权等价物**。L4 AES-256-GCM 上线（P1-1）后，「谁能读」第一次获得密码学强制（持 L4 密钥者可读）；ABE 注入后进一步细化到属性级（按席位/密级/域差异化发钥）。三步是同一问题的递进近似，每步的边界如上表如实标注。

### 5.4 ABE 注入后的治理位（候裁定）

- **AA（属性权威）角色归属**：审计局兼任 AA 存在权力集中风险（AA 可向任意属性集发钥；审计角色本应独立于密钥发行）——分立方案与兼任方案均列，候主权人裁定（§10）。
- 属性撤销：ABE 撤销机制（属性版本化/中介重加密）复杂度高，注入前须有选型论证报告，本稿不预设方案。

## 6. HSM 密钥托管、隔离与透明加解密

### 6.1 L0 托管目标态与过渡态

- **目标态（HSM）**：L0 根密钥托管于硬件密码模块（国密认证 HSM，候采购/注入）；隔离要求三条：① 根密钥不出界——对外仅暴露派生/签名服务（L1 派生在 HSM 内完成，导出的是 L1 而非 L0）；② 激活采用双人规则/分割知识（split knowledge），单一运维者不能独立动用 L0；③ 离线冷介质备份密封保存，备份件 SHA3-512 指纹登记 MANIFEST（承 A 盘迁移治理 MANIFEST 指纹归档纪律，AGENTS.md「迁移治理闭环五件」）。
- **过渡态（现状，如实）**：本网络**无 HSM**。L0 以离线冷介质存储 + AES-256-GCM 密封信封 + 指纹登记承载；操作面仅持有 L1 及以下派生品。**本稿明确标注：过渡态防护等级不等价于 HSM**（无硬件防拆、无物理隔离保证），过渡态时长与 HSM 注入决议候主权人裁定。

### 6.2 透明加解密：SDK 包装层与钩子落点

**降门槛原则**：业务席代码零改动——加解密全部收敛于 SDK 包装层，业务方继续以明文调用。

**钩子落点（实测定位）**：`burn/a2a-plan-50k/a2a_bus_client.py` 之 `build_envelope(uid, message_id, text, seg=None)`（**:147**，构造 A2A 0.3.0 message/send JSON-RPC 信封，parts[].text 承载正文）。
批注：引用 a2a_bus_client.py:147-164 实读；信封字段 id/messageId/role/parts 口径见该函数 docstring。

**包装次序（发送侧）**：

```
业务方 send(text 明文)                      ← 调用面不变
  └─ build_envelope(...)  构信封            ← 现状保留
      └─ [crypto 钩子 C1] 载荷加密：
           parts[].text → AES-256-GCM(L4@kv, nonce=12B 随机)
           → base64( nonce ‖ ciphertext ‖ tag ) 回写 parts[].text
           → 信封增列 kv 标签（§3.3）
      └─ [crypto 钩子 C2] 签名：
           X-Seat-Sig = HMAC_SHA3_512(key, seat + raw_body)[:32]
           ★ 签名覆盖的是「加密后」的 body 字节 —— 承 SPEC §1.2
             「text 取原始请求体」口径：raw body 即最终上线字节
  └─ send_with_retry(endpoint, envelope)    ← 现状保留
```

**接收侧镜像**：验签（kv 查钥，常量时间比较）→ 按 kv 取 L4 解密 → 明文交业务回调。验签失败即拒（strict 期），解密失败单独归因（kv 缺档 / 密文损坏）入 auth 日志。

**元数据分区决策（本稿立场）**：信封元数据（kind/priority/ttl/reply_to/kv）**保持明文**，仅 parts[].text 载荷加密。理由：桥侧路由依赖 kind 浅取（SPEC §2 伪代码 `peekKind(rawBody)` 从 rawBody 正则浅取，parse 失败即 null——若 kind 入密文，桥侧路由与对账日志全盲）；广播总线模型下端到端密文本就只能由持钥接收方解，桥不解密、只路由密文，这与「透明加解密」的桥侧零改造目标一致。代价：元数据对旁路窃听者可见（消息类型/优先级/路由关系泄露面）——如实挂账，缓解措施为元数据最小化（不在 kind/reply_to 中携带业务语义），候跨席商榷。

**兼容策略**：密文回写 parts[].text（字符串位不变）还是新增 parts[].kind="ciphertext"，涉桥席与全网席位解析器，**候跨席协议评审**（P0-2 一并商榷），本稿不单边定稿。

## 8. 一致性窗口（BASE/ACID 综合框架）

### 8.1 框架定位

本网络台账体系是 **AP 优先**系统：总线可用性与分区容忍为先，一致性以**最终一致 + 周期对账收敛**承载；审计对账单与 Merkle 锚是收敛的**验证面**，不是同步面。理论参照（BASE 与 ACID 对比）原样保留主权人指定链接：

### 8.2 现状窗口（定性 + 实证）

  批注：引用 SECURITY_MASTER_REPORT.md §三「口径面 2 条」。

### 8.3 收敛路径（三阶段）

1. **度量**：上述配对统计落地，异步窗基线入账（对账单新列「窗龄」）——先有数再谈收敛，不拍脑袋定 SLA。
2. **压缩**：三个既有机制并行压窗——① epoch 批量入账（5h 边界 flush，§3.2 锚复用）；② strict 签名（伪造消息被拒后，对账噪声下降，真窗可辨）；③ 幂等去重（`make_idempotency_key = sha256(origin+ts)[:16]` 已实现，a2a_bus_client.py:141，重试不产生重复叶）。
3. **锚定**：每 epoch Merkle 根 commit→push，使「账实一致」的验证周期由对账单日级收敛至 epoch 级（5h），最终至 commit 延迟级（分钟级，**待实测**）。

### 8.4 同步一致性的限定适用面

**只有 L3/凭据/开通类消息升格为同步校验**——读己所写经主脸回拨实测（承总报告过渡纪律「不信单源广播」），其余一切消息维持异步最终一致。代价：同步回拨 RTT × 该类消息量；该类消息占比与吞吐影响**待实测**（数据面：auth 日志 kind 列 + 对账单）。**不得**将同步面扩大到全量消息——那会把 AP 系统改造成对总线可用性单点依赖的 CP 系统，与本网络「撞墙即停、切通道、等窗口」的额度现实冲突。
