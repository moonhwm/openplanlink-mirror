## 二、审批链条款

### （一）适用范围

1. 下列情形适用三级审批链，未经审批链通过不得对外承诺：
   - **涉资源事项**：额度重置卡真跑、通道开通/关停、端点创建与变更、凭据交付与轮换安排的对外发起；
   - **涉资金事项**：任何可能产生真实货币支出的动作（含第三方付费服务开通、付费配额购买承诺）；
   - **对外承诺事项**：以 OpenPlanLink A2A 网络名义对外部主体（其他生态席位、第三方厂商、社区）作出的承诺、声明、工单接受与协议性表态。
2. 不适用情形（免审批链，按现行章程执行）：例行的 esc.trace 留痕、心跳与对账、撞墙即停后的通道切换、经验播报、既获批工单的执行推进。免审批情形的边界有争议的，按「就高不就低」原则报审批链，由主权人裁定归类。

### （二）三级审批链程序

1. **动议席提案**：动议席以工单形态（承 COMMS_FINE_MANAGEMENT_v1 任务六态生命周期）提出提案，必载字段：事项类别（资源/资金/对外承诺）、影响面、成本估算、替代方案、风险与回退路径。
2. **筹备组审议**：筹备组对提案作合规性、必要性与成本三面审议，出具审议意见（通过/退回补正/否决）及理由；审议意见以 esc.trace 留痕，入对账轨道。
3. **主权人拍板**：审议通过的提案报主权人终审；主权人可批准、否决或修改后批准。主权人拍板为终局，拍板记录即授权凭据。
4. **筹备组否决后的复核程序**：筹备组出具「否决」的，动议席可修正提案后重新提起，亦可向主权人申请复核；复核申请须同附筹备组否决理由与动议席异议理由双方文本，由主权人终局裁定——维持否决或推翻否决径行批准，两者均为终局。复核期间该事项冻结，不得对外承诺或产生消耗。
5. **主权人主动发起事项的归轨**：主权人主动提出的资源、资金与对外承诺事项，不设动议席提案与筹备组审议前置——主权人径行拍板即视同完成第三级，拍板记录即授权凭据；筹备组仅作事后留痕归档与对账复核，该事后复核不构成事前审批，亦不阻却事项执行。

### （三）违例处置

1. 未经审批链通过对外承诺的，所涉消耗按 AUDIT_BUREAU_v1「无留痕消耗」同类追责，涉资金事项另报主权人裁定责任；对外承诺未经授权的，由动议席即时撤回声明并留痕更正。
2. 紧急避险例外：撞墙、安全事件等须即时处置的，可先处置后 24h 内补报审批链全链条记录；此例外不得适用于资金支出与不可逆对外承诺。

## 五、GPL-3.0 不适格条款

### （一）判定

1. 凡经网络提供调用之组件，GPL-3.0 判定不适格（含 GPL-2.0）：GPL 家族 copyleft 义务以「分发副本」为触发点，纯网络服务（SaaS）模式不分发副本，义务链条在服务边界处断裂，构成 "ASP/SaaS loophole"——第三方可取用 GPL 代码修改后闭源运营网络服务，社区对修改版无源可索。
2. 故 GPL-3.0 不得作为本网网络服务场景的默认许可；网络服务化场景一律改判适格分层。

### （二）适格落层

1. 经网络提供调用之组件，须落 **AGPL-3.0** 层（AGPL-3.0-only，§13 Remote Network Interaction 将开源义务扩展至网络交互，封堵闭源逃逸）；对核心算力调度等敏感组件的云化托管场景，再叠加 **SSPL-1.0** 层（source-available 全服务端开源要求）。
2. 例外：仅本地运行、确认不作为网络服务向第三方提供的内部部署，不触发叠加层，仅按 AGPL-3.0-only 层约束。

### （三）交叉引用

1. 本条与 `opensrc/openplanlink-mirror/LICENSES.md` 第二节「GPL-3.0 网络服务场景不适格判定（SaaS 漏洞）」同源同效，其四点理由（触发点错位、SaaS 漏洞后果、AGPL §13 封堵、SSPL 再加固）与历史效力边界（第四节：变更前版本按其时点协议、fork 依 fork 时点合法存续、宽限期安排、多平台三端一致性）作为本条解释基准。
2. 与第四条衔接：第三方组件 SBOM 登记时须同时标明其许可落层判定；GPL-3.0 组件拟经网络提供调用的，按本条改判或在引入前否决。

## 六、SDD 工程章节：SOP 驱动 CI-CD Loop 吸收 SDD 规范先行思想的三步提案

### （一）方法基线

1. **倒置要点**：SDD 的核心是「代码服务于规范」（Specifications don't serve code — code serves specifications）；spec.md 即真相源，先对齐再构建（agree before you build）。
2. **核心循环要点**：Spec（/specify → 用户故事 + 验收标准）→ Plan（plan.md / data-model.md / contracts）→ Tasks（tasks.md 可并行任务）→ Implement（生成代码），循环迭代而非串行；维护即演进规范，调试即修复错误规范。
3. **AI 适配要点**：以自然语言规范消除实现鸿沟、保障一致性、把变更变成正常工作流，根治 Vibe Coding 的上下文漂移与幻觉。
4. **工具谱系**：Spec-kit（门禁型）、OpenSpec（流动型）、Superpowers（流程重于提示）——本网按需择用，不强制单一工具。

### （二）工作区映射（既有实践印证）

1. **cann-recipes-infer 映射**：其 AGENTS.md 行为约束（先理解再行动 / 回到 skill / 证据优先 / 事实不推断 / progress.md 持久化）即 SDD 循环的 Agent 化对应物；其「三 agent 工作流 + progress.md」构成 Spec→Implement→Review 闭环。
2. **huashu-design 映射**：其三方向硬门（100% 不可豁免）即生成前验收闸；brand-spec.md / product-facts.md 即「规范制品模板先于实现」；任务路由表与 99 处配方库即 Plan/Tasks 工程化。
3. 映射结论：两工作区已各自验证 SDD 思想的局部形态，本案将之系统化为 A2A 全网三步，属既有实践的收敛而非另起炉灶。

### （三）融入三步

1. **第一步·Spec 模板**：A2A 每条 SOP 增设 spec.md 前置段，必载四项——目标、席位视角用户故事、验收标准、边界豁免；模板参照 huashu-design 规范制品模板与 cann-recipes-infer 统一流程规范，字段级约束风格对齐 COMMS_FINE_MANAGEMENT_v1（字段缺失即视为 SOP 未定稿）。由此，SOP 从步骤清单升级为可验证意图源。
2. **第二步·验收闸**：CI-CD Loop 产出提交点增设 Phase -1 式门禁——执行前核对 spec 验收标准、执行后逐项对账；门禁不可跳过（同 huashu-design 三方向硬门之不可豁免性）；门禁结果入 esc.trace 留痕，复用 AUDIT_BUREAU_v1 轨道供筹备组对账与质询。
3. **第三步·规范版本追踪**：SOP spec 纳入 INDEX.md 同款 SHA3-512 前 32 位指纹追踪（python hashlib 现算，禁手填），并挂接 COMMS_FINE_MANAGEMENT_v1 设定 gov.* 版本 ACK 制：规范变更即出新指纹 → 各席 48h ACK → CI-CD 以新指纹重放对账，实现「维护=演进规范」的 A2A 化。
4. 三步的先后：①Spec 模板与③指纹追踪可并行铺开；②验收闸依赖①的四项字段就绪后启用。铺开进度由筹备组在对账单列示，不设全网齐步时限。
